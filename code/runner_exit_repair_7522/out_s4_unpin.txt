S4  THE ANCHOR OF A CENSUS IS NOT THE ANCHOR OF A COMPARISON
==============================================================================

==============================================================================
S4a  THE RULE, STATED ONCE
==============================================================================

  A baseline pinned to a revision is:

      CORRECT for a COMPARISON.  The question is `did this move`, and
      the answer needs a fixed side.  Anchored to HEAD, a comparison
      compares the repaired tree with itself and reports no change
      forever -- mg-821e's finding, and the reason for the pin.

      BLIND for a CENSUS.  The question is `what exists`, and the
      answer must see the current world.  Anchored to a revision, a
      census cannot contain anything added after it -- not because the
      rule is wrong but because the world it is asked about is stale.

  The two uses want different anchors.  Where both appear in one file,
  they are named; S4e checks that they are.

S4c  THE COMPARISON THAT MUST KEEP ITS PIN -- measured both ways
==============================================================================

  mg-c2b3's K3d asks `did any committed transcript move`.  It is a
  COMPARISON.  Run it at the pin and again anchored to HEAD:

      anchored to bee07a1        166 file(s) changed, 42 transcript(s)
      anchored to HEAD             0 file(s) changed, 0 transcript(s)

  Anchored to HEAD the question is `does the worktree differ from
  itself`.  On a COMMITTED tree the answer is 0 BY CONSTRUCTION -- it
  would print a clean bill for any repair whatsoever.  The 0 above is
  this probe's own uncommitted edits if it is run mid-repair, and 0
  once they land; either way it is a fact about the worktree and not
  about the repair.  The pin is the whole content of that check.

  MEASURED: the pinned side sees 166 files, the HEAD side sees 0.

==============================================================================
S4f  THE GENERAL FORM, ON THIS SECTION
==============================================================================

  S4 is a probe about the anchor of an enumeration, so the question it
  owes is what ITS OWN enumerations are anchored to.  Every call, with
  which kind it is:

   1. S4b `scan(ref=None, ...)`   CENSUS      -- unpinned, on purpose.
   2. S4b `scan(ref=PINNED, ...)` COMPARISON  -- pinned, because the
      pinned answer is one side of the 2x2 being compared.
   3. S4c `changed_since(PINNED)` COMPARISON  -- pinned, and S4c is the
      row that shows why removing that pin would empty it.
   4. S4d `git log -1 -- <tree>`  CENSUS      -- unpinned; it asks when
      the tree last moved in the world as it stands.
   5. S4e `L.read(K2, None)`      CENSUS      -- unpinned; it reads the
      file as it is now, which is the only state whose wording matters.

  The branch that CANNOT exhibit the defect, with the reason: S4 makes
  no claim that anything is ABSENT from the world.  Every negative it
  prints is `not found by THIS rule at THIS anchor`, and all four
  combinations are printed, so a reader can see the rule and the anchor
  that produced each answer instead of one number with neither.

  THE LIMIT, stated rather than omitted: the runtime-path rule finds
  the SITE but cannot name the TARGET TREE, because the path is
  assembled from a variable and this is a line-local scan.  Rows in
  that state print `(path built at run time)` rather than being
  dropped -- a row that says `I cannot name the target` is a census
  entry and a dropped row is not.
