K3c  SETTLING C2 -- the one claim that needed a NON-ZERO exit
==============================================================================

  C2 asserts a runner exits non-zero when B1 is restored.  A swallowed
  status would have broken it, so it is the one row the defect could
  not have flattered.  What has to be true for C2's non-zero to be the
  REAL one is narrower than `the block contains no pipeline`, and the
  first draft of this section checked the wider thing and scored 4 of 4
  BAD against a block that is in fact sound.  The block DOES contain
  pipelines.  They are inside the failure HANDLER:

      E2OUT=$(python3 ../species_extent_d633/e2_crosssection.py) || {
          echo "$E2OUT" | grep 'STANDING UN-STRUCK' || true
          echo "E2 CROSS-SECTION FAILED -- ..."
          exit 1
      }

  The three things that actually have to hold, each measured:
    A  the line whose status is read is an ASSIGNMENT FROM A COMMAND
       SUBSTITUTION with no pipeline -- so the status is the checker's.
    B  the handler ends in an UNCONDITIONAL `exit 1`, so nothing inside
       it can turn a failure back into a success.
    C  every pipeline inside the handler is `|| true`, so it cannot
       abort the handler before that `exit 1` is reached.

  species_repair_a4ef      on disk   37    True   True   True(1) ok

  A, B and C hold at both revisions.  C2's non-zero was always the

  ONE MORE THING C2 COULD HAVE COME FROM, and it is worth naming

==============================================================================
K3e  THE GENERAL FORM, ON THIS SECTION
==============================================================================

  K3 is a script that decides whether other scripts' verdicts were
  discarded, so the question is whether K3 discards its own.  What was
  checked, and the branches that cannot exhibit it, with reasons:

   1. Every subprocess in K3b is `subprocess.run(cmd, ...)` with a LIST
      argv and no `shell=True`.  There is no shell, so there is no
      pipeline, so `returncode` is the target's own status.  That is
      the branch that CANNOT exhibit the defect, and the reason is
      structural rather than a promise about how it is called.
   2. `returncode` is READ on every path, including the timeout path,
      where it is None and prints as `-` instead of as 0.  A timeout
      rendered as 0 would be this defect wearing a different hat.
   3. K3b's own effect on the tree is measured (git status before and
      after), because several targets mutate and restore the worktree
      and a restore that silently failed would corrupt K3d's answer.
   4. K3d compares against the PINNED bee07a1, not HEAD.  Anchored to
      HEAD it would compare the repaired tree with itself and report
      zero changes forever -- mg-821e's finding, in this file.
   5. The one thing K3 CANNOT do, stated because a stated limit is
      checkable and an omission is not: it cannot re-run the affected
      targets at every historical commit.  It settles the R3 claims at
      HEAD and at the revisions the claims name, and says so in the
      rows themselves rather than in a footnote.
