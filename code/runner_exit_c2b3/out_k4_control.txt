K4c  THE STUBS ARE NOT DOING THE WORK -- a control on the control
==============================================================================

  A stub harness can pass for a reason that has nothing to do with the
  runner: if the stubs never ran at all, `reach` would be empty
  everywhere, `q_reach[-1]` would not exist and every row would score
  BAD -- which is the safe direction, but a baseline that silently
  reached nothing would make every row unscoreable while still
  printing a full table.  So:

    sites whose BASELINE reached zero stubs: 0
    sites whose baseline exited non-zero:    8
      (allowed, and named: several runners end with a `grep` over
       out_*.txt that stubs do not populate.  The scoring does not use
       the baseline's exit code for anything -- only its reach.)

  And the second direction, which is the one a stub harness usually
  gets wrong: with NO stub failing, does the post-repair runner still
  reach the end?  If the repair had broken a runner outright, every
  `fixed` row would still be green while the runner was useless.

==============================================================================
K4d  THE GENERAL FORM, ON THIS SECTION
==============================================================================

  K4 is a script that runs scripts and reads their exit codes, so it
  is the most exposed part of this instrument.  Enumerated:

   1. `run()` uses subprocess.run with a LIST argv, no `shell=True`,
      no pipe.  `returncode` is the runner's own status.  This is the
      branch that cannot exhibit the defect and the reason is that
      there is no pipeline for a status to be taken from.
   2. Every verdict here is a CONJUNCTION of the exit code and the
      reach.  That is not belt-and-braces: the defect under repair is
      precisely the separation of `printed a failure` from `exited
      non-zero`, so an instrument that scored only one of them would
      be reproducing the defect while testing for it.
   3. The pre-repair arm is run from `git show bee07a1:...`, a pinned
      revision, not from HEAD.  Against HEAD both arms would be the
      repaired text and every row would pass trivially -- mg-821e's
      finding (41ac5d4), applied to this file.
   4. K4c is the control on the control: it checks the baseline
      actually reached the stubs and that the repair did not change
      what runs when nothing fails.  Without it, `fixed` could be true
      because the runner was broken rather than because it was fixed.
   5. What K4 does NOT establish, stated: that the batteries pass.
      The stubs replace them.  K3b is where the real targets run.
