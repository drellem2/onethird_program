P1a  THE PUBLISHING COMMIT, DERIVED AND NOT NAMED
==============================================================================

  A figure from a whole-repository census is a fact about a REVISION.
  mg-56dc's own first run scored a defect against itself for comparing
  a HEAD derivation with a transcript produced on another tree.

  AND THERE ARE TWO REVISIONS HERE, NOT ONE -- which is a distinction this
  probe's first draft collapsed and this ticket's own commit exposed.  It
  read `git log -1 -- <transcript>` and called the answer *the revision
  the figure is a fact about*.  Those are the same revision only until
  somebody REGENERATES the transcript -- and regenerating it is what this
  ticket does, so the moment the repair was committed the derivation
  returned THIS TICKET'S OWN COMMIT and the probe re-derived a 12/14
  census against a transcript stating 9/10 and called it a disagreement.
  A publisher is not a pin.  Both are printed and each is used for the
  question it answers:

      the FIGURE's revision -- what the four artifacts
      state their `9` at, and where it must re-derive       973ca61
      the transcript's CURRENT publishing commit            5533bdb

      the two coincide                                      no -- expected after this ticket

  A NON-COINCIDENCE IS NOT A DEFECT AND IS NOT SCORED.  What WOULD be a
  defect is the figure failing to re-derive at the revision the prose
  pins it to, and that is checked in P1b below and IS scored.  The pin
  must resolve, though -- a revision named in prose that no longer exists
  is the staleness this arc keeps recording:
      `973ca61` resolves as a commit                        yes

P1f  THE CLASSIFIER CANNOT SEE O1 AT ALL -- its axis is the other one
==============================================================================

  THE HEADLINE OF THIS PROBE, and it refutes my own P1g prediction.  I
  predicted the label-reading classifier would disagree with the value's
  true grain on at least one row BEFORE the repair and on zero after.
  It disagrees on the same row before AND after, and the reason is not
  that the repair failed -- the reason is that the classifier's grain
  axis is SITE vs EXECUTION and O1's defect is ROW vs SITE, which is a
  distinction BELOW ITS RESOLUTION.  Read out of `lib56dc.SITE_WORDS`:

      `sites         `  classifies as  SITE
      `rows          `  classifies as  SITE
      `basenames     `  classifies as  SITE
      `source lines  `  classifies as  SITE
      `executions    `  classifies as  EXECUTION
      `runs          `  classifies as  EXECUTION

  `rows` and `sites` are THE SAME GRAIN WORD to this instrument, and
  correctly so on its own terms: both range over source rather than over
  runs, which is the F1 distinction it was built for.  So a count
  labelled `sites` holding a ROW value is, to the sixth instrument,
  a row with the right grain word on it.  IT PASSES.

  THIS IS THE ANSWER TO THE BRIEF'S INSTRUCTION TO CHECK THE CLASSIFIER.
  mg-56dc did not find T1c with this classifier and could not have; it
  found it by re-deriving the quantity at two grains, which is what
  `exec_site_rows`/`exec_sites` are for.  A label-reading check is
  necessary and is not sufficient, and the gap between those two is
  exactly one defect wide -- the one it was pointed at.

  What the test below therefore measures is NOT the classifier's error
  rate.  It is the size of the blind spot: rows where the label declares
  a grain the classifier accepts AND the value is independently
  re-derivable as the OTHER source-side grain.  There is exactly one
  such row in this artifact -- the outside column -- and it is the row
  O1 is about.  Put to both versions:

      as published at 973ca61      label declares SITE   value  10  -> is the ROWS count
          *** IN THE BLIND SPOT: stage `label`, so the grain word
              is on the label itself and the classifier ACCEPTS
              it, while the value is the ROWS count
      repaired, run now            label declares SITE   value  14  -> is the ROWS count
          *** IN THE BLIND SPOT: stage `label`, so the grain word
              is on the label itself and the classifier ACCEPTS
              it, while the value is the ROWS count

      blind-spot ROWS, PUBLISHED version                   1
      blind-spot ROWS, REPAIRED version                    1
      blind-spot ROWS, both versions summed                2

  IT IS STILL 1 AFTER THE REPAIR, AND THAT IS NOT A FAILED REPAIR.  The
  row the test picks is whichever row matches `outside`, and after the
  repair the FIRST such row is `...ROWS outside it, across 7 distinct
  basenames` -- a row whose label says ROWS, holds the row value, and is
  correct.  The classifier calls it SITE because `rows` and `basenames`
  are both SITE_WORDS, so this test cannot tell that row from the one it
  was built to catch.  THE TEST INHERITS THE BLIND SPOT IT IS MEASURING.
  That is a defect of THIS probe, recorded rather than tuned away: the
  honest instrument for O1 is the two-grain re-derivation in P1b, which
  needs no labels at all, and P1e's ledger, which reports what the label
  SAYS without claiming it is true.  A label-reading test cannot audit a
  label -- and that sentence is the whole of why `mg-03d1` exists and is
  told to check the classifier rather than to run it.
