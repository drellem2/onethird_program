S6b  THE TRACE HOOK CANNOT SEE OUTSIDE ITS OWN PROCESS
==========================================================================

  SD2   an `open` audit hook sees only the PROBE's own process
        A probe that reads a transcript by spawning `cat`, `grep`, or a
        second `python3` opens nothing in the traced process, so this
        sweep records it as not reading its own transcript.  It is a
        FALSE NEGATIVE of the same kind as the text rule's, one layer
        further in, and the number of probes it could apply to is:

      ...STEPS run in S2 whose probe spawns a subprocess at all     120
          ^ one unit of that number is one step
      ...STEPS run in S2 in total                                   422
          ^ one unit of that number is one step

      Most of those `subprocess` calls are `git`, not `cat`.  The bound
      is stated as a BOUND -- 120 is the most this could have cost --
      rather than as a measurement of what it did cost, because
      measuring that needs a second instrument this ticket did not
      build.

==========================================================================
S6c  TWO DEFECTS FOUND IN THIS RESOLVER BY ITS OWN SELFTEST
==========================================================================

  SD3   the resolver invented probes called `can`, `the` and `ridge`
        `step "F2: can the V6 row go red?" f2.py` was split on
        whitespace, so argument 2 was the word `can`.  Three trees'
        steps were wrong and every one of them looked like a filename.
        Found by validating each parsed path against the disk, not by
        reading the output.  Fixed with `shlex`; T3 holds the line.

  SD3a  the trace counted a WRITE as a READ, and then I MISATTRIBUTED the evidence for it
        `sys.addaudithook`'s `open` event fires for both, and the first
        version of this hook logged only the path.  A probe that WROTE
        its own transcript would have been recorded as READING the file
        its run had emptied -- the exact false positive this suite was
        built to remove from the text rule, one layer further in.
        The hook now records the mode.  MEASURED EFFECT: 0 steps of the
        422 write their own transcript, so the fix changed no count.

        AND THAT IS THE HALF WORTH KEEPING.  What sent me looking was
        two transcripts left MODIFIED by an early pass, and I wrote
        into the instrument that their own probes had written them.
        They had not: probes of OTHER trees wrote them, having been
        killed by this suite's timeout before their cleanup could run.
        A rigorous fix, a confident mechanism, and the mechanism was
        wrong -- which is this arc's own recurring failure, committed
        here inside the sweep for it.  The real defect is SD6c.

  SD3b  the restore rested on the files happening to be TRACKED
        `run_probe` emptied a transcript and put it back with
        `git checkout --`.  Git cannot restore a file it does not
        track, so on T4's untracked fixture the transcript stayed
        empty -- and the assertion that CHECKS the restore is the
        thing that caught it.  Every tree in the sweep is tracked, so
        no number here was ever affected; the guarantee was resting on
        a coincidence, which is this ticket's own subject.  `run_probe`
        now keeps the bytes itself and writes them back.

  SD4   a `shift` on the same line as an assignment was invisible
        `want="$1"; shift` is two statements and was read as one, so
        every positional parameter after it was off by one and the
        `expect` trees resolved to a probe named `0`.  Fixed by
        splitting on `;`; T1 carries both argument orders side by side
        because that is the error that does not look like an error.

S6f  THE ONE THIS SUITE CANNOT ANSWER ABOUT ITSELF
==========================================================================

  SD6b  42 of 422 steps were KILLED before they could answer
        A probe killed at the timeout may never have reached the
        line that opens its own transcript.  S2 records it as
        not-reading, and the truth is not-known.  Every count in
        S2b is a LOWER BOUND, and S2a says so where the number is
        printed rather than in a footnote.  The population that is
        exact is the 380 steps that finished.

  SD7   A and B are two runs, not one run observed twice
        `diff(A, B)` is attributed to the shape.  The determinism
        control in S3 re-runs B and drops any step where B != B', which
        catches a probe that varies BETWEEN RUNS.  It does not catch a
        probe that varies WITH THE CLOCK in a way that happens to be
        stable across two adjacent runs and not across the minutes
        between A and B.  No row is currently attributed to that, and
        no row is currently ruled out of it either.
